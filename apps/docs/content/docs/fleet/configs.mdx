Installing a MITM is half the job. Aegis, Atlas and GoCheats all read a JSON file
next to themselves and do nothing useful until it has the correct parameters.

Youu can fill that file on the **device group**, in **Settings → Device groups → MITM
data**.

## What a group declares

| Field                | What it is                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| **MITM package**     | The scanner these boxes run. Also what the [MITM column](/docs/fleet/health#the-mitm-column) shows. |
| **Column header**    | Shorter name for that column. Defaults to the last dotted segment.                                  |
| **Config file path** | Where the file goes on the box, eg. `/data/local/tmp/aegis_config.json`.                            |
| **Config JSON**      | The file's contents, with placeholders.                                                             |

The **Fill from** buttons put in the real shapes for Aegis, Atlas and GC,
paths and key sets.

## Putting boxes in a group

One box: the **Group** select on its device page. Many: pick them on **Fleet**
and press **Change group** in the bar at the bottom, the same place **Rename**
lives. The dialog says where the selection is now and how many actually move,
boxes already in the target group are left alone.

Moving a box changes what it installs, not what is on it: the new group's
config, its install hooks and its concurrency cap apply from the next deploy.
Nothing is pushed at the moment of the move.

## Placeholders

Anything a box has to say about itself is a placeholder, substituted per device
before the file is written.

```json
{
  "authBearer": "s3cret",
  "deviceName": "{{device.name}}",
  "rotomUrl": "http://rotom.lan:7072",
  "workers": 8
}
```

Available: `device.id`, `device.name`, `device.serial`, `device.model`,
`device.manufacturer`, `device.androidVersion`, `device.abi`, `device.localIp`,
`device.publicIp`, `device.rotomOrigin`, `device.rotomDeviceId`,
`device.workers`, `group.name`.

`device.workers` is how many workers a Redroid container is configured for, set
per machine on its [Machines](/docs/fleet/redroid-hosts) page. It is what makes
a machine's capacity a number the dashboard owns — containers times workers —
rather than one hard-coded into the group's config, where it would be the same
for every machine in the group.

<Callout type="warn" title="A group that mixes containers and real hardware">
  Only a container has a worker count, so `{{device.workers}}` is empty on a TV box — and an empty
  known placeholder is refused when the config is rendered, naming the box. That is the refusal
  working, and the fix is a group per kind rather than a default nobody chose.
</Callout>

Two things are refused rather than papered over:

- **An unknown placeholder.** `{{device.nmae}}` would otherwise be written
  through literally, and a scanner started against that is worse off than one
  never configured. Caught at Save.
- **A known placeholder with no value on a box.** Substituting `""` is how a
  whole site ends up reporting to Rotom under the same blank origin. Caught when
  the config is rendered for a deploy, naming the box and the field, and logged
  as a warning on that box's job.

<Callout title="rotomOrigin is empty until Rotom matches the box">
  So a first deploy on a fresh fleet often refuses it on most boxes. That is the
  refusal working. Either use `{{device.name}}`, which every box has, or deploy
  again once the Rotom sync has run.
</Callout>

## When it is written

One path: **with the install.** A rollout of a group's own MITM carries that
group's config (if toggled on). The agent writes it after the install verifies and **before** the
post-install hook.

Saving a group writes to the database and nothing else. An edited config reaches
the fleet on the next deploy of that group's MITM (if toggled on), and not before.

## How it lands

The agent takes the `config` object off the install job and:

1. Writes to a temp file and **renames** it into place, so a scanner reading the
   file while it is replaced sees the old bytes or the new ones, never a
   half-written middle.
2. Reads the file back and reports its sha256. That answers "what is on the box",
   where hashing what the hub sent would only answer "what did the hub mean".

A config that cannot be written **fails the job**, rather than leaving a scanner
running on someone else's settings. The downloaded bundle is kept, so the retry
costs an attempt and not a second download.

<Callout type="warn" title="The config holds credentials">
  `authBearer`, `deviceAuthToken`, an email address. It is never written to the hub's log, never
  into an audit entry.
</Callout>
