A box can be online, heartbeating every twenty seconds, and scanning nothing:
the scanner died, Pokémon GO fell out of focus, an ANR dialog is waiting for
somebody to press ENTER, the loop stalled. None of that shows in the fleet
table, because by every measure it has the box is fine.

**Settings → Monitoring** turns those into rules. A rule is a signal, how many
bad readings in a row it takes to count, and a ladder of what to do, soft
first, hard second.

The **Monitoring** page in the sidebar is it's history: what the rules saw
and did across the fleet, which is where "why did that box reboot at 3am" is
answered.

## What it watches?

| Signal                                     | Answered by                  | What it means                                         |
| ------------------------------------------ | ---------------------------- | ----------------------------------------------------- |
| **Service is down**                        | a probe, or the process list | The scanner's service is not running                  |
| **App is not in focus**                    | the box                      | Something else owns the screen — usually the launcher |
| **App is not responding**                  | the box                      | The package is sitting on an ANR dialog               |
| **Health check is failing**                | a probe                      | The scanner is logging faults faster than work        |
| **Loop has stalled**                       | a probe                      | The scanner is alive and has stopped doing anything   |
| **Box is unreachable**                     | the hub                      | The socket has been gone past the offline timeout     |
| **Rotom lost the box**                     | the hub                      | Rotom is not seeing it, or would not hand it work     |
| **Rotom has the box but no workers**       | the hub                      | Connected to Rotom with nothing allocated on it       |
| **Scanner is allocated and doing nothing** | the hub                      | A worker is open and no requests go through it        |

The first five are knowable only on the box, so they need a recent agent, the
tab counts how many boxes are behind, and rules skip a box that cannot answer.
The last four the hub sees for itself and work on every box today; all of them
need [Rotom turned on](/docs/fleet/rotom).

The three Rotom signals are deliberately exclusive, so one fault never lights
two ladders: a box Rotom has lost is only ever **Rotom lost the box**, a box
with nothing allocated is only ever **no workers**, and **doing nothing** is
read only where both of those are fine.

Two caveats worth knowing before switching them on:

- **No workers** is normal on a fleet with more boxes than accounts. The spares
  are idle on purpose. Scope that rule to a group, or raise its threshold.
- **Doing nothing** is silent unless Rotom measures request rates, which it
  only does in `requests` mode, or `proxy` mode with `inspect`. Where it does
  not measure, the signal reads unknown rather than idle — which is why turning
  it on cannot start rebooting a fleet that never reports a rate.

### On a machine

A rule declares **which kind of device it is about** — a box or a
[machine](/docs/fleet/redroid-hosts) — and four signals exist for the second:

| Signal                  | Answered by | What it means                                                                         |
| ----------------------- | ----------- | ------------------------------------------------------------------------------------- |
| `HOST_MEMORY_LOW`       | the hub     | Free memory **plus free swap**, under the rule's percentage floor                     |
| `HOST_DISK_LOW`         | the hub     | Free space under that floor, on the filesystem docker keeps its images and volumes on |
| `HOST_DOCKER_DOWN`      | the hub     | The agent is up and the docker daemon is not                                          |
| `REDROID_INSTANCE_DOWN` | the hub     | A container that should be running is not                                             |

Swap counts as headroom in the first one, because on these machines it is
exactly what stands between fifty workers and the OOM killer. A machine with no
swap reports zero rather than nothing, so adding it is safe and a genuinely
absent reading stays unknown.

The last two are read from what the machine said on its **last** heartbeat, not
from its row:

- `HOST_DOCKER_DOWN` is the agent reporting while docker does not answer it. The
  machine's stored docker version deliberately keeps the last one ever seen, so
  a newer agent's finding is not wiped by an older one's silence — which makes
  the column history, and a daemon being down a question about right now. A hub
  that has just restarted reads **unknown** for one heartbeat, which the startup
  grace already covers.
- `REDROID_INSTANCE_DOWN` counts only the instances marked **present**: a
  removed one keeps its row, and counting it would have a drained machine alarm
  forever. All the known ones running is healthy even while another is still
  unknown, so a machine recovers on the container that came back instead of
  waiting for one nothing has looked at.

<Callout type="info" title="A machine mid-converge is left alone">
  Its containers are being created or replaced because somebody asked for that, so instances
  legitimately are not running. It is skipped for the same reason a box mid-install is: the only
  thing a rule could report is the damage the hub itself asked for.
</Callout>

`RESTART_INSTANCE` is the narrowest remediation in the project:
`up -d --no-recreate`, naming only the services that are down. A container that
is running is not touched, nothing is removed, and the machine is never
rebooted — which is the whole point of the action existing, since rebooting
takes every other box on the machine down for one box's fault.

`AGENT_OFFLINE` needs nothing new: pointed at machines, it already means exactly
the right thing, because a machine is a `Device` and its socket is gone the same
way a box's is.

#### Why these are signals and not probe rules

A shell probe on the machine looks cheaper — one `HEALTH_CHECK_FAILED` rule per
check, no enum values, no code. It does not work, and the way it fails is
silent: `rulesFor` dedupes on **signal + package name** and keeps one winner per
key, so three `HEALTH_CHECK_FAILED` rules with no package collapse into one. Two
of your three checks would simply never run — no error, no probe, nothing in the
feed to say why.

<Callout type="warn" title="And a probe on a box reads the machine's load, on every box at once">
  Inside a container, `/proc/loadavg` and the thermal zones are the **host's**. A
  `HEALTH_CHECK_FAILED` probe that greps either is not reading one box's state; it reads the
  machine's, identically, on all ten boxes on it. One cause then trips ten ladders, and the per-box
  ceilings do not help because each box is under its own. Nothing in the code can catch this — the
  probe is a string you typed and the reading is perfectly valid. Use `HOST_MEMORY_LOW` and
  `HOST_DISK_LOW` on the machine, or a box's own `cpuPercent`, which [is genuinely its
  own](/docs/fleet/redroid-hosts#cpupercent-is-the-honest-per-box-cpu).
</Callout>

## The ladder?

A rule does the gentle thing first and the expensive thing only when the gentle
one did not work:

```
Scanner offline
  failure 1 → restart the app
  failure 2 → reboot the box
```

The counter resets the moment the signal goes good, so a box that recovers
never reaches the reboot. A rung already spent is not spent again — except the
**last** one, which repeats at the cooldown, because there is nothing stronger
left to try.

| Action                                 | What it runs                                          |
| -------------------------------------- | ----------------------------------------------------- |
| Only tell me                           | nothing                                               |
| Restart the app                        | `am force-stop {pkg}` then relaunch                   |
| Kill the app                           | `am force-stop {pkg}`                                 |
| Clear the cache and restart            | force-stop, delete `/data/data/{pkg}/cache`, relaunch |
| Send ENTER                             | `input keyevent 66` — dismisses an ANR dialog         |
| Start the service                      | `am startservice …`                                   |
| Run a command                          | whatever you type                                     |
| Reboot the box                         | the same reboot the device page sends                 |
| Restart the scanner in Rotom           | Rotom's own `restart` action                          |
| Drop the scanner's connection in Rotom | Rotom's `disconnect` — the box reconnects             |
| Reboot the box through Rotom           | Rotom's own `reboot` action                           |
| Restart one Redroid container          | from the machine that runs it, not from inside it     |

**Restart one Redroid container** is the host-side counterpart of _restart the
app_: the smallest thing that fixes a wedged instance. `Reboot the box` is
deliberately **not** overloaded to mean "reboot the VPS" — that takes every box
on the machine down at once, which is a much larger decision than the signal
that would reach for it.

It runs on the machine, over the machine's own socket, so a machine that is not
answering has the rung **refused rather than spent** — the ladder still has it
when the machine comes back. It is counted as a hard action for the same reason
a reboot is: the container _is_ the box, so restarting it cold-boots that
Android and every app on it comes back from nothing.

The three Rotom actions travel **Rotom's socket, not the agent's**, which is what makes
them the only remediation left on a box whose agent has died — every other
action on the list needs the box reachable from Magnemite. The mirror of that is
also true and worth planning a ladder around: Rotom cannot act on a box it has
lost, so on a **Rotom lost the box** rule the bottom rung is the agent-side
`Reboot the box`, and on the other two it is `Reboot the box through Rotom`.

`Reboot the box through Rotom` counts against **reboots per box per day** and
sits under the post-reboot grace exactly like the agent-side one. A different
socket, the same boot cycle.

Every shell-backed one takes an **override command**, `{pkg}` standing in for
the rule's package. The catalog exists so an alert can say "cleared the cache
and restarted" rather than quoting a command line; the override exists because
your MITM is not the one this was written against.

## Probes

Three signals need the box to look at something, and what to look at differs
per MITM — so the probe is part of the rule:

- **Shell command** — runs as root, passes on exit 0, optionally also having to
  match a pattern. `dumpsys activity services | grep -e MappingService` is the
  whole "is the scanner up" check.
- **Pattern in a log** — reads the last N lines of a file and counts matches.
  Can also fail when nothing has been written for a while, which is what a
  stalled loop looks like from outside.
- **HTTP endpoint** — a GET from the box itself; 2xx is healthy.

A log probe can carry a **second** pattern for work getting done, and fail only
when faults outnumber it — ten "seconds since last ping" lines mean nothing
next to a hundred completed jobs and everything next to two:

```
Log file          /data/local/tmp/atlas.log
Lines to read     200
A fault           \[HEALTH CHECK\] ([0-9]+) seconds since last ping\.
Faults before     10
Work looks like   I \| Worker
```

Probes run every heartbeat, inside **half the beat**. Whatever does not finish
in that budget reports nothing at all — never a failure. They are skipped
entirely during an install, because an install force-stops the scanner on
purpose and every probe would report the damage Magnemite asked for.

## The numbers

The master switch is on **Settings → Monitoring**. Everything else is the **How
it watches** card on **Settings → Tuning**, because every number in it is
measured against the heartbeat or the offline timeout, which sit directly above.

| Setting                         | Default | What it does · what a bad value costs                                                                                                                           |
| ------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Act on what it sees**         | off     | Off, no probe is sent and nothing is touched. Rules can still be written.                                                                                       |
| **Ask Rotom every**             | 10s     | One request for the whole fleet, whatever its size. Everything Rotom-shaped is this fresh at best. Floored at 5s, which is what Rotom's own dashboard polls at. |
| **Rotom stale after**           | 600s    | How long since Rotom saw a box before that counts as disconnected. Floored at two sync intervals, or it alerts on the sync's lag.                               |
| **Grace · after a reboot**      | 600s    | Shorter than the box takes to boot and its own reboot reads as unreachable — so it is rebooted again, forever.                                                  |
| **Grace · after a hub restart** | 180s    | A restart drops every socket at once; without this, a deploy looks like a fleet-wide outage.                                                                    |
| **Actions per box per hour**    | 4       | Circuit breaker. Past it, one critical alert and the box is left alone. This is what bounds a rule that turns out to be wrong.                                  |
| **Reboots per box per day**     | 6       | The same, counted separately, because a reboot costs a scanning session and the other actions do not. Reboots sent through Rotom count here too.                |
| **Repeat an alert after**       | 30 min  | The same signal on the same box is not announced again inside this. The action still happens and is still recorded.                                             |
| **Keep history for**            | 30 days | How long the Monitoring feed is kept. 0 keeps it forever.                                                                                                       |

The monitor pass itself is not configurable: it runs once per heartbeat,
because a pass reads what the boxes last said and they say it once per beat.
"Box is unreachable" counts from the **offline timeout** — to wait longer,
raise that rule's own threshold, which is per group.

<Callout type="warn" title="The two graces and the two ceilings are the safety of this feature">
  Everything else is tuning. Those four stand between a useful watchdog and a fleet rebooting itself
  in a loop, and each exists because that has happened to somebody.
</Callout>

## Where alerts go

Three channels, on the same tab, each set up on its own: **Discord**, **ntfy**
and **web push**. They are independent in every way that matters — its own
credential, and one being broken says nothing about the other two. Configure
none of them and the rules still run: remediation never depends on a
notification going out.

**Which rules reach which channel is decided on the rule**, in **Announce it** —
a dropdown of the three, and picking none is a rule that acts quietly. Set up a
channel here; choose who uses it there.

None of the cards has a minimum severity. There used to be one per channel, and
two filters in series meant a rule set to announce could silently not, with
nothing on the rule to say why. One filter, on the rule, where somebody looking
for the reason is already looking.

What the channels do share is the repeat window. The point of it is that a
flapping box does not announce itself thirty times, and a window per channel
would let it do exactly that by taking turns.

### Discord

A **webhook URL** — empty turns the channel off and leaves the rules running —
and an optional **role to ping**, used on critical only: a mention on every
warning is how a channel gets muted, which costs you the alert that mattered.

### ntfy

A **server** — the public `https://ntfy.sh`, or your own — and a **topic**.
Empty topic turns it off. Install the ntfy app, subscribe to the topic, and a
fault buzzes the phone with a link straight to the box.

On ntfy.sh a topic is the only thing protecting it: anyone who guesses the name
reads your alerts, so pick one nobody would. The **access token** is for a
self-hosted server or a reserved topic; empty publishes anonymously, which is
what a public topic wants.

A rule's **Severity** drives ntfy's own priority dial, which is what decides
whether a phone in a pocket makes a sound: `INFO` is quiet, `WARN` is high, and
`CRITICAL` is max — which on Android gets through Do Not Disturb. It changes how
the alert arrives, never whether it does.

### Web push

A notification from the dashboard itself, on the desktop or phone of whoever
asked for one. Nothing to install and no third party in the path.

Two halves that look like one card and are not. The switch is a fleet-wide
setting, saved with **Save** like everything else here.
**Notify this browser** is per browser and per person — it asks for the
notification permission, registers a service worker and stores an endpoint only
that browser can be reached at — so it takes effect on the click. Alerts then
arrive with every tab closed.

It needs a VAPID keypair in the hub's environment; without one the card says so
rather than offering a button that cannot work. Generate it once:

```sh
npx web-push generate-vapid-keys
```

and set `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT`. Keep them:
a push service only accepts messages signed by the key it saw when a browser
subscribed, so regenerating the pair silently unsubscribes everyone. There is
no way for the server to ask a push service what it still holds — a browser
that was cleared or revoked is only discovered when it answers 404 or 410, and
its row is dropped then.

<Callout type="info" title="Safari and iOS need the Home Screen">
  iOS only allows web push for a site added to the Home Screen. Until then the card says the browser
  cannot do it, which is accurate rather than a bug.
</Callout>

Individual rules can be silenced without being switched off — **Announce it**
set to nothing. "Pogo not in focus" ships that way: a box briefly on the
launcher is common enough that announcing every one teaches people to ignore
the channel. The same control is how a rule goes to Discord but not to a phone
at 3am, without either channel having to know about it.

A rule that announces can also announce the **all-clear** — the second switch
next to it in the rule dialog, off by default. On, the fault is followed by one
more message when the signal goes good again, which is how "Box unreachable"
becomes "Box unreachable recovered" in the channel rather than only in the
feed. It goes to the same channels the fault did — a recovery announced
somewhere the fault was not is a message about nothing — and it ignores the
repeat window, which has just been filled by the fault it ends. Only an episode that actually reached the rule's threshold
gets one — an all-clear for a fault nobody was told about is noise.

Press **Send test alert** before trusting any of it — the button is on all
three cards and sends through every channel that is set up, reporting each one
separately, because "it worked" is useless when the question is which of three
is misconfigured. It has no rule behind it, so it ignores both the per-rule
channels and the repeat window on purpose.

A channel that stops working never stops the remediation — the box is still
restarted, and the Monitoring page records that the message did not arrive. An
event counts as announced when **any** channel took it: a Discord message that
landed is not made un-sent by ntfy being down at the same moment.

## Scope

A rule applies to every box, or to one device group. A group-scoped rule
**replaces** the fleet-wide rule for the same signal and package rather than
adding to it, or two ladders would race over one fault and the box would be
restarted twice. That is the seam for a fleet running Atlas at one site and
Aegis at another.

**Which kind of device** is the other half of that filter, and it is not
optional: a rule is about boxes or about
[machines](/docs/fleet/redroid-hosts), never both. Existing rules are about
boxes, which is the default and what every seeded rule is.

| A rule aimed at | Evaluated against          | What the wrong side would do                                                             |
| --------------- | -------------------------- | ---------------------------------------------------------------------------------------- |
| boxes           | `kind = BOX` devices only  | A box rule on a VPS reads a scanner's absence as a fault on a machine that never ran one |
| machines        | `kind = HOST` devices only | A host rule on a box measures a disk and a daemon that are not the box's                 |

Both mistakes would **act**, not just alert, which is why the filter is a field
on the rule rather than something the evaluator infers.

The group is also where that site declares which MITM it runs and what to write
into its [config](/docs/fleet/configs). A group-scoped rule and its group's MITM
package are two halves of the same answer, so they are worth keeping in step: a
rule probing Atlas's log on a group that runs Aegis is a rule that never fires.

The seeded rules are not invented: their thresholds and ladders are what
[aconf](https://github.com/TechG3n/aconf)'s `atlas_monitor.sh` has done on this
hardware for years. The probe strings are Atlas's, which is exactly why they
are editable rows.
