A spare Mac is good hardware to point at this, and the hardware is not the
problem. What stops it is one layer down, and no amount of configuration gets
past it.

## Why the Mac itself cannot be the machine

Redroid is **Android in a container**, not a virtual machine. Every container
shares the host's Linux kernel and talks to Android's `binder` driver in it.

macOS has no Linux kernel. There is no `modprobe`, no `/dev/binder`, no
`/proc` — which is also where this project's agent reads a machine's load,
memory and CPU from. There is no `darwin` build of the agent either: it is
cross-compiled for `linux/arm64`, `linux/arm`, `linux/amd64` and
`windows/amd64`, and nothing else.

Docker Desktop does not rescue it. It runs containers inside a Linux VM of its
own, whose kernel ships no `binder_linux` and will not take one.

<Callout type="info" title="The arch check passes, which is the confusing part">
  On Apple Silicon `uname -m` says `arm64`, so the bootstrap's first step — the one that refuses
  x86_64 — is perfectly happy. It dies at the next one, on `apt-get`, long before it reaches the
  thing that actually cannot work. A Mac failing this is not a near miss.
</Callout>

## What to run instead

**A Linux VM on the Mac.** The machine Magnemite manages is the VM; the Mac is
the hypervisor and Magnemite never knows it exists. This is also Redroid's own
answer to the question — its maintainer's reply to "how do I run this on an M2"
is _set up a VM and run it there_
([redroid-doc#609](https://github.com/remote-android/redroid-doc/issues/609)).

**Parallels Desktop** and **UTM** are both reported working with an Ubuntu arm64
guest. **OrbStack is not**: its Linux machines are containers on a shared
LinuxKit kernel, which is the same wall Docker Desktop hits.

What the VM needs:

|                                     |                                                                                                         |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **arm64**                           | A `linux/arm64` guest. The fleet's bundles carry an `arm64-v8a` split and the agent matches ABI exactly |
| **Debian or Ubuntu**                | The bootstrap installs with `apt-get`, and gets `binder_linux` from `linux-modules-extra-$(uname -r)`   |
| **A 64-bit-only image**             | Not the fleet's default, and the one thing on this page that is not just configuration — see below      |
| **RAM**                             | Whatever you give the VM is what the capacity planner divides up — the Mac's total is invisible to it   |
| **Reachable once**                  | The hub needs one outbound SSH connection to it, and only for provisioning. See below                   |
| **Its own IP, or a forwarded port** | A NAT'd VM is fine; a bridged one is simpler                                                            |

Everything after that is the ordinary
[provisioning](/docs/deployment/redroid-bootstrap) — same form, same script,
same steps.

## Getting the hub to it, once

This is the only part a machine at home makes harder, and it is harder for
exactly one moment. **After provisioning, nothing ever connects towards the
machine again**: the agent dials out and holds the socket, and scaling,
converging, metrics, exec, logs and re-running the setup all travel back down
it. No static address, no open port, no dynamic DNS.

Four ways through that one moment, easiest first.

<Steps>

<Step>
### Nothing at all, when the hub is already on that network

Worth checking first, because at home it is often already true and there is no
work in it. A self-hosted hub on the same LAN as the Mac reaches a **bridged**
VM directly — the VM takes an address from your router like any other machine,
and the hub opens an ordinary connection to it. No router page, no forwarding,
nothing exposed.

One value has to be right for this, and it is not the SSH side.
`MAGNEMITE_PUBLIC_URL` is written into the machine's own config as the hub's
address, so `localhost` makes a machine dial _itself_ — it provisions, reports
every step fine, and never appears online. Set it to the hub's address **on
that network** before provisioning anything that is not the hub's own box. The
hub already listens on every interface, and plain `http://` is accepted and
becomes `ws://`, so a LAN address needs no certificate.

</Step>

<Step>
### Or forward a port

On your router, forward a port to the VM's `22`, give the VM a reserved lease
so the target stops moving, and then **Machines → Add machine** with your
public address and that port.

Translation is fine: forward external `2222` to the VM's `22`, type `2222`, and
the firewall still ends up correct. The hardening step does not take the port
you typed as dictation — it opens the **union** of that port, whatever
`sshd -T` resolves, and every `Port` line in `sshd_config` and its drop-ins. A
spare rule costs nothing and a missing one costs the machine, which is the
whole reason it guesses wide rather than precisely.

</Step>

<Step>
### Or join them to a mesh

Any path that lets the hub reach the VM's SSH once will do. The hub needs a
host and a port it can open a TCP connection to, and nothing more — so a mesh
VPN works, needs no router page, and keeps the address stable when your ISP
moves you.

The thing to check is that the VPN has a **Linux** client, since it is the VM
that has to join, not the Mac. Tailscale and NordVPN's Meshnet both do.
Windows-only meshes — Radmin VPN among them — cannot be used here for that
reason, however convenient they are between desktops.

A reverse tunnel from the VM is the same idea with no third party: the VM dials
out and forwards its `22` back, so nothing is opened on your router either. It
has to stay up for the length of one provisioning and not a minute longer.

</Step>

<Step>
### Or provision it by hand, with nothing open at all

The one-click form is a driver for a script that does not need it. Copy the
pieces to the VM and run it there — no inbound connection ever.

From the repo, on the Mac:

```sh
make agent
ssh you@vm 'mkdir -p /tmp/magnemite-bootstrap/redroid && chmod 700 /tmp/magnemite-bootstrap'
scp agent/bin/magnemite-agent-linux-arm64 you@vm:/tmp/magnemite-bootstrap/magnemite-agent
scp agent/host/bootstrap.sh you@vm:/tmp/magnemite-bootstrap/
scp agent/redroid/Dockerfile agent/redroid/magnemite-start.sh \
  agent/redroid/magnemite-root-grant.sh agent/redroid/magnemite.rc \
  you@vm:/tmp/magnemite-bootstrap/redroid/
```

No Go on the Mac? Take the binary out of the hub's own image instead, which
also guarantees it is the build that hub expects:

```sh
docker cp <hub-container>:/app/agent-bin/magnemite-agent-linux-arm64 .
```

Then, on the VM, as root:

```sh
cd /tmp/magnemite-bootstrap

MAGNEMITE_SERVER=https://agents.example.com \
MAGNEMITE_TOKEN=<host enrollment token> \
MAGNEMITE_NAME=mac-vm \
MAGNEMITE_SERIAL=<any stable, unique value> \
MAGNEMITE_SSH_PORT=22 \
MAGNEMITE_IMAGE=magnemite/redroid:2 \
sh ./bootstrap.sh
```

Two values are worth being careful about. The token comes from **Settings →
Enrollment** with **Enrols** set to **A machine** — a box token cannot bring a
machine up, and the only symptom is a device that never grows a Machines page.
And `MAGNEMITE_SERVER` is the **hub's** URL, which is not the dashboard's.

</Step>

</Steps>

<Callout type="warn" title="Provisioned by hand means adopted by hand">
  The one-click path remembers what you asked for and applies it the moment the machine dials in: it
  adopts the machine and brings its containers up. A machine provisioned by hand has no such record,
  so it enrols, appears under **Machines**, and sits there marked `not adopted` — with **Adopt** and
  the instance count waiting for you on its page. That is two clicks, and nobody guesses them from a
  bootstrap that reported every step as fine.
</Callout>

## The 32-bit half of Android, and the CPUs that cannot run it

This is the one item on this page that is not configuration, and it is not
really about Macs — a Mac is just the first machine most people own that has
the problem.

An arm64 Android normally ships two zygotes, 64-bit and 32-bit, because AOSP
expects to run 32-bit apps. Whether the 32-bit one can start at all is a
property of the **CPU**, and Arm has been removing AArch32 generation by
generation:

| Core               | Machines                                       | AArch32 at EL0 |
| ------------------ | ---------------------------------------------- | -------------- |
| Neoverse N1        | Ampere Altra, AWS Graviton 2                   | yes            |
| Neoverse V1        | AWS Graviton 3                                 | yes            |
| Neoverse N2        | Alibaba Yitian 710                             | yes            |
| Neoverse V2        | **AWS Graviton 4**, Google Axion, NVIDIA Grace | **no**         |
| Neoverse V3        | **AWS Graviton 5**                             | **no**         |
| Apple M1 and later | **every Apple Silicon Mac**                    | **no**         |

On everything in the bottom half the 32-bit zygote has nothing to run on.
Redroid publishes `_64only` images for exactly this reason, and its
maintainer's standing advice for Apple Silicon is to use one.

The fleet's image is not one of them. It builds on
`abing7k/redroid:a11_magisk_arm`, which is Android 11 from
`redroid/redroid:11.0.0-latest` — and upstream has `_64only` variants from
Android **12** up, never for 11 — Android 11 predates the problem. So there is
no prebuilt Magisk-prerooted 64-bit-only Android 11 anywhere, because there is
no Android 11 to build it from.

<Callout type="info" title="Which is why nothing is wrong today">
  Every machine this fleet has run on executes AArch32 at EL0, so both zygotes start and the image
  is correct. This is a constraint on what to **buy** next, not a fault to go and fix — and the
  bootstrap's first step will not catch it, because a Graviton 4 answers `aarch64` exactly like a
  Graviton 3 does.
</Callout>

<Callout type="warn" title="It will look like a network problem">
  The reported symptom on an M1 under Parallels is a container that runs and an `adb` that never
  connects ([redroid-doc#336](https://github.com/remote-android/redroid-doc/issues/336)) — Android
  never finishes booting, so nothing inside it answers. Here that surfaces as an instance marked
  **running, not enrolled**: the container is up, the agent in it never dialled out. That row is
  worth trusting. It is the state the instances table exists to tell apart, and on one of the CPUs
  above it points at the image rather than at the network.
</Callout>

The escape hatch is already in the data model: **the image is per machine**, so
one Mac VM can run a different Android from every VPS without touching them.
Building that image means a 64-only base at Android 12 or newer with
[`ayasa520/redroid-script`](https://github.com/ayasa520/redroid-script), which
takes `12.0.0_64only` as a target, then this repo's `agent/redroid/Dockerfile`
layered on top of the result.

<Callout type="info" title="There is no UI for it yet">
  `RedroidHost.image` and `RedroidHost.gpuMode` are both per-machine columns and neither has a field
  on the machine's page, so overriding one today is an `UPDATE` in psql followed by a **Re-run
  setup** to build the tag and a converge to move the containers onto it. Worth knowing before
  planning around it.
</Callout>

## Two things that bite a machine at home and not a VPS

- **A Mac that sleeps is a machine that disappears.** `AGENT_OFFLINE` fires on
  the same timeout a dead VPS gets, and the offline sweep cannot tell the two
  apart. Put a machine like this in a [group](/docs/fleet/redroid-hosts) of its
  own and give its monitoring rules a longer threshold, or none. Turning off
  sleep for the VM's host is the other half.
- **The VM's memory is the only memory there is.** The capacity line divides
  what the VM reports, not what the Mac has, and the fleet-wide defaults — 4 GB
  per container with 2 GB held back — mean a 4 GB VM fits nothing. Give it more
  than you think, or lower both in **Settings → Tuning** and watch the sentence
  under the instance count do the arithmetic for you.
